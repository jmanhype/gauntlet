## Description
## USER INTENT
The owner needs a verified local recovery path before research history can be considered durable evidence.

Observable outcome: the owner can run the declared command, inspect or display its output, and verify that the implementation returns the declared result, stores its immutable artifact, and emits the corresponding hash-verified event.

## Context (Embedded)
Implement a local backup and restore verifier for required durable classes: trial/event ledgers and heads, evidence descriptors, immutable policies, raw source snapshots, model checkpoints, and Decision Snapshots with owner extensions. Create a content-hashed bundle manifest, verify it, restore into an empty destination, and prove ledger/manifest verification succeeds. Exclude regenerable reports/indexes, credentials, private owner material, signatures, and unredacted secrets. Fail closed on missing, corrupt, truncated, or unverified content and refuse a non-empty destination.

Phase 1 boundaries:
- No order placement, real-money exposure, public API, daemon, multi-tenant access, or social claim.
- Immutable local evidence and replayability govern implementation choices.
- Unknown or unregistered inputs are gate-critical failures.
- Failures return machine-readable errors and never fabricate a score or silently substitute data.
- No SQLite or other database engine dependency is permitted.

## OUT OF SCOPE
- Remote replication or cloud provider selection: owner decision outside Phase 1.
- Scheduled long-running backup daemon: prohibited Phase 1 surface.
- Live order placement or real-money exposure: Phase 1 remains RED with zero real-money exposure.
- Public API access or public performance claims: explicit business non-goals.

### Acceptance Criteria (story contract)
1. Backup includes every required durable class: ledger trials/events/heads, descriptors, policies, raw source snapshots, checkpoints, and Decision Snapshots/owner extensions.
2. The bundle manifest records content hashes, relative paths, byte counts, source head hashes, and a deterministic aggregate root.
3. Verification detects missing, extra-unexplained, truncated, rewritten, or corrupt content before restore.
4. Restore into an empty destination recreates required files and passes ledger, descriptor, snapshot, and manifest verification.
5. Restore refuses a non-empty destination and never partially overwrites an existing data root.
6. Regenerable reports/index projections are excluded by policy and can be rebuilt after restore.
7. No credential, private owner key, signature, or unredacted secret enters the backup.

## Testing Requirements
- Unit: Test manifest hashes, required-class selection, exclusions, destination refusal, and corrupt/missing content.
- Integration tests: MANDATORY (no mocks). Create a real local bundle containing all required classes, restore it to a fresh temporary data root, rerun verification, then corrupt a copy and prove restore fails without touching the source.
- Commands to run: `uv run pytest tests/integrity/test_backup_restore.py`.
